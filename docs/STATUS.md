# Status

Milestone 1 through an isolated WebAssembly guest. Working, not a game.

## Implemented

- JSON manifests, closed schema, semantic versions and ranges.
- Discovery of module folders on disk, and the same packages bundled for the console.
- API compatibility, required and optional capability dependencies, duplicate ids.
- Slots: singleton, policy, registry, pipeline, subscriber, service.
- Module-owned slots. A child package connects without changing the parent or the host.
- Cycle detection, depth limit 8, deterministic order, conflict and ambiguity refusal.
- Transactional failure: bad manifests are isolated; graph failures and init exceptions roll back. Shutdown on rollback includes the module that failed, and skips any module that had not entered that phase.
- Headless demo and the browser console over one `compose()` function. The public entry is `src/foundations/index.ts`, also the package export `"."`.
- Caller-initiated dispatch. `publish` fans one event through a subscriber slot and keeps going after a throw. `runPipeline` folds a value through a pipeline slot and stops at the first failure. `callService` invokes the one provider of a service slot and returns its value. A handler that returns a promise is awaited, and a rejection is a failure of that call. A contribution to those three kinds must already be callable or registration fails. None of these is a tick.
- Composition fingerprints name module versions, slot contracts, dependency edges, and contribution order. Package order does not change the fingerprint. A different version or contribution order does.
- Isolated WebAssembly guests. Discovery reads manifests and wasm bytes and does not import or instantiate. Each composition owns its workers. A reservation is one hold, charged before the worker starts and refunded once if the load fails or the session releases, including when those two overlap. `release` resolves after it terminates them, including a worker that was still loading, and including when composition fails and when shutdown throws. An in-flight call is counted before it starts, including when the call throws synchronously, so release does not wait forever. `dispose` waits for every open session and then refuses new work. Shutdown is single-flight and continues after one module's shutdown failure. Two compositions can run at once, including two versions of the same module id, and one looping guest does not block the other unless a hook-time budget serializes that ledger. The host waits on promises and does not call `Atomics.wait`. Guest memory must declare a maximum. That maximum is `maxMemoryBytes`. The file size is `maxBinaryBytes`, and the two are not the same check. Host memory accounting sums declared linear-memory maxima across open compositions, including in-flight loads. It is not process RSS and it does not include `isolateHeapMb`. Shared memory, 64-bit memory, imported memory, and an oversized or unbounded table are refused before instantiation. The worker repeats those checks and, on Node, runs under a heap, code, and stack cap. `isolateHeapMb` sets that heap cap. The browser isolate refuses the policy instead of ignoring it, and otherwise enforces the same declared limits. Unauthorized imports, including WASI and `node:fs`, are refused before the guest runs. `cgp.log` is linked only when the manifest and the policy both allow it. Lines are capped in UTF-8 bytes and in line count. The drop marker counts toward both, and it is omitted when it cannot fit. Completed sessions retain a bounded number of those logs. ABI inputs must be JSON. A cycle, a bigint, or any other non-JSON value fails the call or the import before the guest runs and does not skip cleanup. A throw while reading an input becomes one host error and is not forwarded. A call with no arguments sends `arg: null` and `args: []`; an explicit `undefined` is refused. ABI handles are minted per composition. A copied or cross-module lookalike is not callable, and a handle from another composition does not enter either guest. Guest JSON is copied so a `__proto__` field cannot change the host prototype. A worker error or a time limit stops that guest, and disposal during either still returns the reservation. Save slices are plain JSON and restore on a new isolate.
- Cross-backend compositions. JavaScript hooks stay on the in-process backend. WebAssembly bytes and ABI handles go to `wasm-isolate`. Nested `{ "dispatch": true }` inside a register payload becomes an ABI handle, so a policy object can carry a guest function. Aggregate budgets (`maxGuests`, `maxTotalMemoryBytes`, `maxTotalBinaryBytes`, `maxTotalHookMs`) are optional, per composition, and enforced only by the isolate. Unset means unlimited. A failed instantiation refunds its charge. Host ceilings sit above those budgets. Guest, memory, and binary charges return on release. Host hook time does not. A set hook budget admits one call at a time.
- One real guest, Dune Growth, plus `examples/wasm-module` and `examples/third-party-module`. Dune Growth is off in the default proof. `scripts/build-wasm-module.ts` regenerates bytes, including a `guest.json` package. `scripts/check-wasm-module.ts` instantiates a third-party package and refuses malformed manifests, non-WebAssembly bytes, hostile imports, and a register result that is not contribution JSON. `scripts/browser-wasm.ts` runs the shared runtime in Chromium. `scripts/verify-wasm.ts` and the foundations workflow compare generated bytes to the generators and typecheck the host, the browser isolate, and `wasm-guest-runtime.mjs`. The repository and those modules are MIT.
- Flora proof (species registry + one growth policy) and Lighting proof (source registry) on the same platform slot.
- Module-owned save slices. The host stores JSON a module exports and restores a slice only when the major version matches. Two slices for one module are refused. A different profile name or fingerprint warns, and slices are still matched by module id. Object keys in a slice are sorted. Array order is kept. If one `importState` throws, the host puts back every slice it wrote in that restore, including the module that threw, and later slices are not applied. If that put-back throws, the notice is `save.rollback`. `captureSave` waits on the same lane as restore, a simulation step, and a mutating service, so it does not record a mixture of those. A service declared `mutates: false` does not take the lane. A service called from `exportState` can still change a later slice; a slice already returned stays as that hook returned it. A save started from inside that composition's hook is refused. One composition's hook does not count as another's. `shutdown()` quiesces the runtime, and dispatch and save then refuse.
- A public entry, `src/foundations/index.ts`, and a copyable starter module. `validateManifest` checks a manifest that has no implementation yet. The console uses that same function. It does not load code.
- Composition profiles. A JSON document pins module ids and exact versions. A missing module or a different packaged version refuses the selection. The host does not upgrade.
- Independent module release package format v1 (accepted ADR 0017): closed `cgp-package.json` descriptors for Wasm Core and JavaScript ESM, strict UTF-8/duplicate-key JSON parsing, portable regular-file package paths, static Wasm/JavaScript checks, raw artifact SHA-256, and canonical `cgp.package-tree/1` identity with fixed test vectors. `scripts/check-module-package.ts` validates a local release directory without importing JavaScript or instantiating Wasm. `scripts/build-module-package.ts` builds a clean release directory from `module.ts` or `module.wasm`, copies it into a separate read-only staging snapshot, validates and re-hashes the staged bytes, and writes a machine-readable release summary outside the package. This package tooling stays outside Foundations. The local content store and `cgp.local-catalog/1` catalog register validated staging snapshots by `cgp.package-tree/1` digest and enforce immutable `moduleId@version` coordinates. Store operations use cooperative cross-process read/write markers: registration takes the exclusive writer marker and waits for active readers to drain; object verification and Wasm project snapshots hold reader markers for complete package-file scans. The Wasm snapshot marker is released after all verified bytes are owned in memory, not at runtime shutdown. Stale reader markers are not reclaimed automatically; writers time out and fail closed until an operator verifies and removes them. This is same-host local-filesystem coordination, not distributed locking. Persistent lifecycle metadata in `.cgp-store-lifecycle.json` records object states, default local-import pins, explicit project-lock pins, and token-owned deletion claims. Project pins are keyed by a stable caller-supplied project ID; lockfiles are not discovered automatically. Registration writes the default local pin before publishing the catalog reference. Legacy stores without a lifecycle sidecar are treated conservatively: each existing catalog object gets a local-retention pin on migration. The explicit GC preview verifies package-tree digests and reports candidate bytes, release associations, age, and checked retention roots. It does not persist migration, create deletion claims, or delete content. The claim primitive marks an unpinned object as `deleting` under the writer gate, blocking new readers and pins. `npm run store:gc-apply -- --apply` rechecks that eligibility, persists deletion intent, renames the object into a same-filesystem tombstone, and removes the tombstone only after the lifecycle record says removal has started. Catalog rows stay. `store:gc-recover --apply` resumes an interrupted deletion and fails closed on ambiguous or symlink state. `store:gc-reconcile --apply` reports token-owned deletion claims and does not release them; `--cancel-claim --digest` revokes one claim without deleting bytes. It does not run during reads or registration. A writer lock is adopted only when its token matches an in-progress deletion and its pid is not alive. Pin management and these GC commands are Node CLI operations; the browser console still handles registration, verification, and project lock creation/resolution. A live Wasm activation acquires a composition lease under `.cgp-store.composition-leases/<uuid>.json` (`cgp.store-composition-lease/1`) before its snapshot and releases that lease only after Foundations shutdown and backend disposal, including when activation fails. The lease is a GC retention root. It does not hold a reader marker, so unrelated store writes can proceed. The release token is not part of the activation result. `npm run store:leases -- --action release` drops one lease by token and does not delete bytes. `release-abandoned --apply` drops a lease whose recorded pid is not alive and also does not delete bytes. Stale leases are not reclaimed automatically and are not cleared by GC, reads, or registration.
- Capability requirements. One matching provider is a dependency. Two matching providers are ambiguous, and the host does not pick one. Naming `moduleId` on the requirement pins the provider. An optional requirement still refuses when more than one provider matches. A module that lists the same capability twice is isolated.
- Resolved order edges. Each edge names the provider, the dependent, and a capability or a module-owned slot. A missing or ambiguous requirement adds no edge.
- A world record table and a caller-driven step, as modules. World Core exposes spawn, remove, and list. World Store keeps the records and the save slice. Step Clock counts only when a caller asks. Step Witness hears that one publish. Neither module runs a loop, and the host does not know what an entity or a step means.
- A caller-driven simulation step, outside the Foundations. Simulation Core owns the system pipeline, the completion slot, and the ledger services. Systems return proposals. The ledger itself refuses a commit that is not the open step, not the next tick, not the same entity ids, or outside 0 through 1000, and a refused commit leaves the tick and the positions unchanged. The runner opens one step, aborts that mark when the step does not commit, and publishes one completion only after the ledger accepts it. Seed, advance, restore, capture, and a mutating service for one composition run one at a time, in call order. A service the runner calls, and an outside mutating service that arrives while a step holds the lane, run during that step. A capture does not run until those calls and the completion subscribers have finished. `sim.read` declares `mutates: false` and does not take the lane. A subscriber failure is reported and does not roll the tick back. A publish that does not run is reported on `completion`, separate from that list. The host does not roll back a scratch a system wrote during the proposal. Movement is JavaScript. The boundary is a WebAssembly guest. The same inputs, including after save and restore, produce the same ledger on the Node isolate and in Chromium. Nothing advances unless a caller passes the next tick. There is still no loop.
- Cross-language boundary, recorded in [ADR 0020](adr/0020-cross-language-modules.md). The November 2026 index (Python, C, Java, C++, C#, JavaScript, R, SQL, Visual Basic, Go) is reference documentation, not a Foundations export. JavaScript is the in-process implementation. The other nine are not hosted. A guest is unlabeled WebAssembly: a conforming binary is not a C, C++, Go, or Python module. A manifest field `language` is refused. A call or a save slice that reaches a guest is copied JSON. A value that is not JSON fails that call and does not by itself stop the guest. Node and Chromium both observe that interchange. Rust is eleventh and is not claimed. An authoring project may use TypeScript; the author's toolchain emits the release. The format-v1 JavaScript artifact is `module.mjs`. This host does not compile TypeScript. ADR 0018 remains the content store. ADR 0019 remains project lockfiles.

- Node project activation (`activateProject` in `src/packages/project-activation.ts`). One verification pass and one composition lease cover a JavaScript ESM project, a Wasm Core project, or both, before any import or guest start. JavaScript is loaded from snapshotted `module.mjs` bytes only after `javascript: "trusted-in-process"`. That code runs in the Node process with filesystem, network, and operating-system access. It is not sandboxed, and the Wasm import allowlist does not cover it. A closed policy does not import it. Mixed projects use the existing cross backend, so Wasm stays on `wasm-isolate` while JavaScript stays in-process. `activateWasmProject` still refuses JavaScript before a lease. Shutdown runs Foundations shutdown, invalidates package resource views, disposes the Wasm backend, removes the owned JavaScript copies, then releases the lease. Each step is marked done only after it returns. The source path is kept until removal returns. Linux walks the opened directory file descriptor and refuses a directory whose owner mode lacks write or execute, including when the process is root. Windows, macOS, and every other platform that cannot pin that directory against a symlink swap refuse JavaScript before a composition lease, before import, before top-level code, and before a resource view. The error says no lease was acquired. No activation directory is created. A closed policy and Wasm-only activation still run, and CI on Windows and macOS verifies that refusal rather than a successful JavaScript activation. Cleanup does not follow symlinks and does not contain trusted JavaScript. An opted-in JavaScript module may implement `openResources` and receive an opaque view of its own verified package files. Reads use the exact relative path and return copies. The view is not a store path. It stays usable through shutdown hooks and is invalidated only after Foundations shutdown. A Wasm guest in the same project does not gain a resource import. See [Study 010](studies/cgp/010-unified-project-activation.md) and [Study 011](studies/cgp/011-package-resource-access-and-ownership.md).
- Deletion-claim ownership. `store:gc-reconcile --apply` does not drop a token-owned `deleting` claim and does not infer a stale owner from pid or age. The holder releases the claim with its token. `--cancel-claim --digest` is administrative cancellation of that one claim and does not delete bytes.

## Not implemented

- Physics.
- A prepare, commit, and abort protocol for arbitrary module scratch. A system is required to stay pure during a proposal. Completion is the supported place to record a step.
- Rendering.
- Input.
- Audio.
- A scheduler that advances time by itself. A step still happens only when a caller asks.
- Multiplayer networking or replication.
- Hot module reloading.
- Runtimes for Python, C, Java, C++, C#, R, SQL, Visual Basic, and Go. A WebAssembly guest is not one of those languages.
- Enforced permissions for in-process JavaScript. A declared permission is still not a boundary there. The WASM backend does enforce its import allow-list. A cross composition does not make the JavaScript half limited.
- Save migrations beyond a major-version refusal. No disk format beyond the JSON document.
- Automatic stale-reader reclamation, path-backed JavaScript package loading, archive acquisition/import, remote registries, publisher signatures, and provenance verification. A token-owned deletion claim is released by its holder or by an explicit one-digest cancellation. Unrelated stale writer locks are not removed automatically. Stale composition leases are not reclaimed automatically.
- Browser-console activation of stored packages. The console Composition view still composes bundled proof packages. Node activation of stored packages is `activateProject` / `activateWasmProject`. There is no hot reload.
- A Wasm resource import, a browser transport for packaged files, and cross-package resource reads. JavaScript `openResources` is the package-layer view of one verified tree. It is not a sandbox, and it is not available to a Wasm guest. See [Study 011](studies/cgp/011-package-resource-access-and-ownership.md).

## Provisional

- Manifest field names and the six slot kinds.
- Foundations API `1.0.0` and max depth 8.
- Contract compatibility is major-version equality, or exact equality when the connection names a full version. Subscriber, pipeline, and service payloads must be callable at registration. Registry, singleton, and policy payloads are not inspected.
- The in-process backend is opt-in. It still cannot revoke filesystem, network, or operating-system access, and it cannot enforce time, memory, or capability limits. A policy that asks it to is refused. It is not a sandbox.
- `wasm-isolate` is the isolating backend. Guests are owned by the composition that opened them. `wasm-browser` enforces the same declared policy or refuses `isolateHeapMb`. `createCrossBackend` routes one composition across an isolate and the in-process backend. A branded handle goes to that composition's isolate session. A lookalike goes to the in-process half and is not called. A handle from another composition does not enter either guest. Aggregate budgets are per composition. Host ceilings are per backend. A set hook-time budget admits one call at a time.
- A dispatchable payload is a function, an object with a `handle` function, or an ABI handle. A service may return `undefined`. A pipeline stage may not.
- A save payload is whatever JSON the module returns. Same major means compatible. `importState` is the only migration.
