# Status

Milestone 1 through an isolated WebAssembly guest. Working, not a game.

## Implemented

- JSON manifests, closed schema, semantic versions and ranges.
- Discovery of module folders on disk, and the same packages bundled for the console.
- API compatibility, required and optional capability dependencies, duplicate ids.
- Slots: singleton, policy, registry, pipeline, subscriber, service.
- Module-owned slots. A child package connects without changing the parent or the host.
- Cycle detection, depth limit 8, deterministic order, conflict and ambiguity refusal.
- Transactional failure: bad manifests are isolated; graph failures and init exceptions roll back. Shutdown on rollback includes the module that failed, and skips any module that had not entered that phase.
- Headless demo and the browser console over one `compose()` function. The public entry is `src/foundations/index.ts`, also the package export `"."`.
- Caller-initiated dispatch. `publish` fans one event through a subscriber slot and keeps going after a throw. `runPipeline` folds a value through a pipeline slot and stops at the first failure. `callService` invokes the one provider of a service slot and returns its value. A handler that returns a promise is awaited, and a rejection is a failure of that call. A contribution to those three kinds must already be callable or registration fails. None of these is a tick.
- Composition fingerprints name module versions, slot contracts, dependency edges, and contribution order. Package order does not change the fingerprint. A different version or contribution order does.
- Isolated WebAssembly guests. Discovery reads manifests and wasm bytes and does not import or instantiate. Each composition owns its workers. A reservation is one hold, charged before the worker starts and refunded once if the load fails or the session releases, including when those two overlap. `release` resolves after it terminates them, including a worker that was still loading, and including when composition fails and when shutdown throws. An in-flight call is counted before it starts, including when the call throws synchronously, so release does not wait forever. `dispose` waits for every open session and then refuses new work. Shutdown is single-flight and continues after one module's shutdown failure. Two compositions can run at once, including two versions of the same module id, and one looping guest does not block the other unless a hook-time budget serializes that ledger. The host waits on promises and does not call `Atomics.wait`. Guest memory must declare a maximum. That maximum is `maxMemoryBytes`. The file size is `maxBinaryBytes`, and the two are not the same check. Host memory accounting sums declared linear-memory maxima across open compositions, including in-flight loads. It is not process RSS and it does not include `isolateHeapMb`. Shared memory, 64-bit memory, imported memory, and an oversized or unbounded table are refused before instantiation. The worker repeats those checks and, on Node, runs under a heap, code, and stack cap. `isolateHeapMb` sets that heap cap. The browser isolate refuses the policy instead of ignoring it, and otherwise enforces the same declared limits. Unauthorized imports, including WASI and `node:fs`, are refused before the guest runs. `cgp.log` is linked only when the manifest and the policy both allow it. Lines are capped in UTF-8 bytes and in line count. The drop marker counts toward both, and it is omitted when it cannot fit. Completed sessions retain a bounded number of those logs. ABI inputs must be JSON. A cycle, a bigint, or any other non-JSON value fails the call or the import before the guest runs and does not skip cleanup. A throw while reading an input becomes one host error and is not forwarded. A call with no arguments sends `arg: null` and `args: []`; an explicit `undefined` is refused. ABI handles are minted per composition. A copied or cross-module lookalike is not callable, and a handle from another composition does not enter either guest. Guest JSON is copied so a `__proto__` field cannot change the host prototype. A worker error or a time limit stops that guest, and disposal during either still returns the reservation. Save slices are plain JSON and restore on a new isolate.
- Cross-backend compositions. JavaScript hooks stay on the in-process backend. WebAssembly bytes and ABI handles go to `wasm-isolate`. Nested `{ "dispatch": true }` inside a register payload becomes an ABI handle, so a policy object can carry a guest function. Aggregate budgets (`maxGuests`, `maxTotalMemoryBytes`, `maxTotalBinaryBytes`, `maxTotalHookMs`) are optional, per composition, and enforced only by the isolate. Unset means unlimited. A failed instantiation refunds its charge. Host ceilings sit above those budgets. Guest, memory, and binary charges return on release. Host hook time does not. A set hook budget admits one call at a time.
- One real guest, Dune Growth, plus `examples/wasm-module` and `examples/third-party-module`. Dune Growth is off in the default proof. `scripts/build-wasm-module.ts` regenerates bytes, including a `guest.json` package. `scripts/check-wasm-module.ts` instantiates a third-party package and refuses malformed manifests, non-WebAssembly bytes, hostile imports, and a register result that is not contribution JSON. `scripts/browser-wasm.ts` runs the shared runtime in Chromium. `scripts/verify-wasm.ts` and the foundations workflow compare generated bytes to the generators and typecheck the host, the browser isolate, and `wasm-guest-runtime.mjs`. The repository and those modules are MIT.
- Flora proof (species registry + one growth policy) and Lighting proof (source registry) on the same platform slot.
- Module-owned save slices. The host stores JSON a module exports and restores a slice only when the major version matches. Two slices for one module are refused. A different profile name or fingerprint warns, and slices are still matched by module id. Object keys in a slice are sorted. Array order is kept. If one `importState` throws, slices already written in that restore are put back and later slices are not applied. `shutdown()` quiesces the runtime, and dispatch and save then refuse.
- A public entry, `src/foundations/index.ts`, and a copyable starter module. `validateManifest` checks a manifest that has no implementation yet. The console uses that same function. It does not load code.
- Composition profiles. A JSON document pins module ids and exact versions. A missing module or a different packaged version refuses the selection. The host does not upgrade.
- Capability requirements. One matching provider is a dependency. Two matching providers are ambiguous, and the host does not pick one. Naming `moduleId` on the requirement pins the provider. An optional requirement still refuses when more than one provider matches. A module that lists the same capability twice is isolated.
- Resolved order edges. Each edge names the provider, the dependent, and a capability or a module-owned slot. A missing or ambiguous requirement adds no edge.
- A world record table and a caller-driven step, as modules. World Core exposes spawn, remove, and list. World Store keeps the records and the save slice. Step Clock counts only when a caller asks. Step Witness hears that one publish. Neither module runs a loop, and the host does not know what an entity or a step means.
- A caller-driven simulation step, outside the Foundations. Simulation Core owns the system pipeline, the completion slot, and the ledger services. Systems return proposals. The ledger itself refuses a commit that is not the open step, not the next tick, not the same entity ids, or outside 0 through 1000, and a refused commit leaves the tick and the positions unchanged. The runner opens one step, aborts that mark when the step does not commit, and publishes one completion only after the ledger accepts it. Seed and advance for one composition run one at a time, in call order. The host does not roll back a scratch a system wrote during the proposal. Movement is JavaScript. The boundary is a WebAssembly guest. The same inputs, including after save and restore, produce the same ledger on the Node isolate and in Chromium. Nothing advances unless a caller passes the next tick. There is still no loop.

## Not implemented

- Physics.
- A prepare, commit, and abort protocol for arbitrary module scratch. A system is required to stay pure during a proposal. Completion is the supported place to record a step.
- Rendering.
- Input.
- Audio.
- A scheduler that advances time by itself. A step still happens only when a caller asks.
- Multiplayer networking or replication.
- Hot module reloading.
- Enforced permissions for in-process JavaScript. A declared permission is still not a boundary there. The WASM backend does enforce its import allow-list. A cross composition does not make the JavaScript half limited.
- Save migrations beyond a major-version refusal. No disk format beyond the JSON document.

## Provisional

- Manifest field names and the six slot kinds.
- Foundations API `1.0.0` and max depth 8.
- Contract compatibility is major-version equality, or exact equality when the connection names a full version. Subscriber, pipeline, and service payloads must be callable at registration. Registry, singleton, and policy payloads are not inspected.
- The in-process backend is opt-in. It still cannot revoke filesystem, network, or operating-system access, and it cannot enforce time, memory, or capability limits. A policy that asks it to is refused. It is not a sandbox.
- `wasm-isolate` is the isolating backend. Guests are owned by the composition that opened them. `wasm-browser` enforces the same declared policy or refuses `isolateHeapMb`. `createCrossBackend` routes one composition across an isolate and the in-process backend. A branded handle goes to that composition's isolate session. A lookalike goes to the in-process half and is not called. A handle from another composition does not enter either guest. Aggregate budgets are per composition. Host ceilings are per backend. A set hook-time budget admits one call at a time.
- A dispatchable payload is a function, an object with a `handle` function, or an ABI handle. A service may return `undefined`. A pipeline stage may not.
- A save payload is whatever JSON the module returns. Same major means compatible. `importState` is the only migration.
